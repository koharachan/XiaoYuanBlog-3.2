这篇文章整理一次 NodeSeek 讨论中的问题：如果只部署静态网站，怎样在成本、HTTPS、域名数量和国内访问稳定性之间取平衡？原始记录包含 192 个国内测速节点。下面先给结论，再说明测试口径和限制。

## 先看结论

| 方案 | 测试平均延迟 | HTTP 平均耗时 | 失败节点 | 适合谁 |
| --- | ---: | ---: | ---: | --- |
| SCDN | 71 ms | 1.46 s | 5 / 192 | 能接受手动续期、只需要简单静态站 |
| GitHub Pages | 104 ms | — | 159 / 192 | 主要面向海外访问，能接受国内网络波动 |
| CloudFront | 114 ms | 1.60 s | 4 / 192 | 已有 AWS 账号、需要全球分发 |
| 热铁盒 | 159 ms | 1.79 s | 2 / 192 | 能接受平台约束和额外图片托管 |
| EdgeOne | 176 ms | 1.07 s | 2 / 192 | 需要国内访问、多域名或更完整的边缘能力 |

平均延迟不是唯一指标。GitHub Pages 的 104 ms 看起来很低，但 192 个节点里有 159 个失败，国内访问稳定性不能按平均值判断。

## 方案差异

### GitHub Pages

优点是部署简单、免费、和 GitHub 仓库结合紧密。缺点也很明确：国内部分网络或运营商存在访问失败，且平台规则对域名和构建方式有约束。它更适合作为开源项目文档或海外访问站点，不适合把“国内可稳定打开”作为硬指标的个人博客。

### SCDN

本次测试的平均延迟最低，但需要按照平台规则续期，域名和配置能力也比自建 CDN 少。适合页面内容简单、可以接受人工维护的静态站点。

### CloudFront

全球覆盖和生态完整，但国内访问效果受区域、证书、回源和具体分配策略影响。使用自有域名时要提前处理证书和 DNS，不要把“接入 CDN”误认为已经完成国内优化。

### 热铁盒

节点失败数较少，但 HTTP 耗时偏高，而且 HTTPS、图片托管等能力有额外限制。适合对平台限制不敏感的小站，不适合需要完整控制静态资源的项目。

### EdgeOne

本次 HTTP 平均耗时较低，失败节点也少；如果站点主要服务国内访问，或者需要多域名、边缘缓存和更完整的控制面，它是更稳妥的选择。具体免费额度和产品限制要以当前官方页面为准。

## 测试口径与局限

原始数据来自 192 个测速节点，但记录没有完整保留测试工具、具体日期、节点网络类型以及每个方案的完整请求参数。因此这些数字只能作为一次横向参考，不能当作长期 SLA。尤其要区分：

- `ping` 或 TCP 延迟只能说明链路响应，不等于页面完整加载速度；
- HTTP 耗时还会受到 HTML 大小、缓存命中、TLS 握手和回源策略影响；
- 免费方案的额度、续期方式和节点策略会变化，复测时应保留日期和配置；
- 失败节点比平均值更值得关注，建议按目标用户所在运营商再做一次抽样。

## 我的选择建议

- 以国内访问稳定为第一目标：优先看 EdgeOne 或其他国内边缘平台；
- 只要免费、访问者主要在海外：GitHub Pages 仍然省事；
- 已经在 AWS 生态里：CloudFront 的整体控制力更强；
- 只是临时页面或个人实验：SCDN、热铁盒可以先用，但要记录续期和证书限制。

成本最低不等于总成本最低。把人工续期、故障排查、图片外链和国内失败率一起算进去，通常比单看“免费”更接近真实选择。
